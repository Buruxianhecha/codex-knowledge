# 结论强度必须匹配证据强度

> 证据支持到“参与”，就写参与；支持到“盘中”，就写盘中；支持到“成品存在”，就不写运行成功。

## 核心问题

研究和工程报告中最常见的失真，不一定是凭空造假，而是动词和范围被逐步放大：

```text
出现 -> 参与 -> 负责 -> 主导
相关 -> 影响 -> 导致 -> 证明
演示 -> 测试版 -> 上线 -> 稳定生产
盘中价 -> 当日价 -> 收盘价 -> 最终结算价
```

每向右一步都需要新增证据，不能靠措辞润色完成升级。

## 命题分解

一个可审计结论至少拆成：

- **主体**：谁或哪个系统。
- **动作**：做了什么。
- **对象**：作用于什么。
- **时间**：何时、哪个版本。
- **范围**：样本、平台、仓库或环境。
- **强度**：出现、相关、贡献、领导、因果等。
- **状态**：计划、执行、完成、验收、长期稳定。

证据必须覆盖每个关键槽位。缺失部分不能由常识或叙事自动补全。

## 写作中的应用

### 人物与组织角色

提交、论文署名或项目成员页可以支持“贡献/参与”。要写“负责人/领导”，还需要任命、职责说明、本人/机构明确表述或一致的组织证据。

### 传播与社会研究

公开视频、点赞和评论可以支持“内容存在、获得可见反应”。没有平台后台、受众访谈或实验时，不能直接写“造成某种心理或行为结果”。

### 法律与责任

公司自述、媒体评论和法律认定属于不同命题。没有权威裁判或监管决定时，应使用“可能涉及、存在风险、本文分析认为”，不能写“已经违法/已被认定”。

### 平台治理

功能下线是事实，具体动机如果未由平台说明，只能作为多种解释。分析应把法规、架构成本、未成年人风险和商业策略列为解释维度，而不是选一个写成唯一原因。

## 工程中的应用

| 证据 | 合理表述 | 过度表述 |
|------|----------|----------|
| README/部署说明存在 | 已准备部署流程 | 已部署成功 |
| 文件能解析 | 语法检查通过 | 业务功能正确 |
| 4 项 smoke test 通过 | 结构和规则锚点通过 | 全部玩法已验证 |
| 某 SHA 的 CI 绿 | 该提交 CI 成功 | 仓库所有历史都无失败 |
| Blob 一致 | 远端文件与预期一致 | 用户一定能正常使用 |
| 本地 ownerId 过滤 | 测试账户在本机隔离 | 已有生产级授权 |

## 数值的“最终性”也是证据字段

黄金图表曾出现把 2026-08-10 盘中值标作“收盘”的问题。时间序列值至少携带：

- `observed_at`：观察时间。
- `market_date`：所属交易日。
- `state`：实时、盘中、收盘、结算、修订。
- `source`：来源与单位。
- `is_final`：是否最终。
- `supersedes`：是否替代较早快照。

预测、实际、事后标注也必须用独立系列和图例，不能通过颜色或位置让读者猜。

## 不确定性措辞

| 证据状态 | 推荐措辞 |
|----------|----------|
| 直接证据充分 | 确认、显示、记录为 |
| 多来源一致但非直接 | 高度支持、可合理判断 |
| 单一/间接证据 | 表明、提示、可能 |
| 来源冲突 | 存在两种记录、暂不能裁决 |
| 没有证据 | 未确认、当前无证据支持 |

## 行动规则

1. 先写最小可证命题，再决定是否升级。
2. 为关键动词指定所需证据。
3. 主动搜索反证和更弱解释。
4. 资料截止日写入稿件，时效事实过期后重查。
5. 未确认不是空白羞耻，而是研究结果的一部分。
