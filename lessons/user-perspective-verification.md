# 用户视角验收原则

> 任务完成的标准不是“代码生成成功”，而是最终用户实际验证成功；验证声明的强度必须与真实验证层级匹配。

## 来源

- 首次形成：2026-05-25。
- 后续在相册、多个浏览器模拟器、极简 UI 失败复盘和知识库审计中持续复用超过三个月。

## 核心原则

### 一：未验证 = 未完成

在未经过真实结果验证前，不得主动结束任务。命令退出、文件存在、构建成功、宿主接纳、用户路径和重启保持是不同层级，不能互相替代。

### 二：用户实际优先

当“理论结果”与“用户实际结果”冲突时，优先相信用户实际体验。不要先假设用户操作错误。优先排查：环境 → 兼容性 → 缓存 → 编码 → 路径 → 运行时。

### 三：优先复现，而非只分析代码

用户报告问题时，优先尝试在实际环境中复现。如果无法复现，明确列出可能环境差异、潜在触发条件、用户侧可验证信息和下一步排查路径。

### 四：禁止未验证声明

在未经过实际验证前，不使用“现在可以了”“已经完全修复”“大概率没问题”等最终性措辞。可以说“代码层已修改”“构建已通过”“仍缺真机/用户路径验证”。

### 五：重复错误 = 升级风险等级

同类错误被用户重复指出时，提高该问题类型的风险等级，未来任务自动启用更严格的预检与验收。

### 六：验证完整用户路径，而非单个功能

不仅验证功能本身，还验证：

- 用户如何进入页面。
- 用户第一眼看到什么。
- 用户点击/操作顺序。
- 用户是否容易误解。
- 用户是否能顺利完成目标。
- 刷新、重启、换标签页或恢复后是否仍成立。

## 强制验收清单

### P0 必检

- 页面/文件是否能打开。
- 页面是否空白。
- 中文是否乱码。
- 核心功能是否可以点击/使用。
- 响应是否与明确需求一致。
- 明确禁止项是否真的不存在。

### P1 应检

- 样式是否错乱。
- 控制台/日志是否有报错。
- 修改是否真正生效，而不是无效修改。
- 用户操作路径是否通畅。
- 未指定区域是否被意外改变。

### P2 可检

- 移动端/真机兼容性。
- 边缘情况（空输入、超长输入等）。
- 是否影响其他功能。
- 容量、并发、恢复和长时间运行。

## 错误责任机制

以下情况都说明之前的验收不完整：页面打不开、空白、乱码、核心功能无法操作、响应偏离需求、用户实际体验异常、修改后无变化、用户必须重复指出同类问题。

发生后应：

1. 重新检查最终结果。
2. 回溯问题来源。
3. 主动寻找隐藏错误。
4. 分析为什么之前未发现。
5. 把新的门控规则沉淀到 checklist / mistake / pattern。

## 禁止行为

- 未检查就直接交付。
- 仅凭代码正确就认为任务完成。
- 用“应该/理论上/大概率”替代验证证据。
- 只验证局部逻辑。
- 只验证功能，忽略完整用户路径。
- 用户指出问题后仍重复同类错误。
- 为了让报告好看而提高验证等级。

## 主动修复机制

发现异常时：继续排查、测试相邻风险、验证修复是否真正生效、检查边缘情况，并确认没有破坏未要求修改的区域。

## 排查优先级

```text
1. 环境     — 操作系统、依赖版本、PATH
2. 兼容性   — 浏览器/运行时差异
3. 缓存     — 浏览器缓存、编译缓存、CDN
4. 编码     — 字符集、换行符、BOM
5. 路径     — 硬编码路径、相对路径、空格/中文
6. 运行时   — 实际报错、日志、进程状态
```

## 重复错误风险升级

```text
同类错误被重复指出
-> risk: high
-> 相同任务类型启用更严格验收
-> 记录到 mistake / anti-pattern
-> 下次主动预检
```

## 长期目标

降低重复错误，提高真实验收、问题闭环和一次性交付成功率，减少用户重复返工。
