## 核心交付偏好

### 真实完成，不报喜式完成

- 代码生成、脚本退出 0、构建成功和文件上传都不等于最终完成。
- 必须说明验证到了命令、产物、集成、宿主、用户路径中的哪一层。
- 用户实际体验与理论判断冲突时，以用户体验为准并继续排查。
- 对未验证内容使用“待验证/未确认”，不要使用“应该已经可以”。
- GitHub 交付要回读默认分支、HEAD、关键 Blob 和该 HEAD 的 CI。

### 需求边界

- “只、仅、不要、不显示、单文件、保持原样”属于排他性约束。
- 不用主动增加秒数、按钮、说明、动画或其他“有用功能”覆盖明确的极简目标。
- 用户已确认的版本在部署和整理仓库时保持冻结；新增功能先提出，不擅自加入。

### 先满意测试，再付费扩展

- 涉及对象存储、短信、数据库等付费服务时，优先做不付费或低成本测试版验证体验。
- 测试版必须清楚标注边界；本地存储、Mock 登录和公开预览不能包装成正式生产能力。
- 从测试版升级时优先做兼容迁移，不通过清空用户数据获得“干净架构”。

## 写作与研究偏好

- 写作要求深度、详细、事实边界清楚，不只做泛泛摘要。
- 优先一手/官方材料；二手材料回溯原始来源。
- 区分事实、分析、建议和无法确认事项。
- 人物角色不夸大：`contributor` 不写成 `lead`。
- 公司自述不写成法律认定；单案例和公开热度不写成总体因果。
- 时间敏感稿件写资料截止日；后续引用前重新核验。
- 材料可使用编号、时间码和 SHA-256 保证版本可追溯。
- 数值图表要区分实时、盘中、收盘、预测、实际和事后标注。
- 对外稿件不得使用真实姓名；署名按当次要求设置。2026-08-02 的相关稿件最终署名为“AI”，不能自动类推到所有文档。
- 交付 Word/PDF 时检查文件名、正文、页眉页脚、作者属性和隐藏元数据。

## 软件安装

- 必须询问再安装软件，不擅自操作。
- 避免 C 盘，除非别无选择。
- 模仿已有安装位置和命名风格。
- 安装后告知实际路径，并检查桌面快捷方式、图标和启动路径。
- 快捷方式名称和图标必须匹配目标品牌，不能用依赖工具图标代替。

## 编码风格

- 实用主义；模块常量可用短名，但核心函数/类要清晰。
- 快速原型阶段可容忍内联导入等折中，先跑通再优化。
- 第二个同接口实现出现时抽公共层。
- v1 完成后先硬化：安全、配置、死代码、依赖和鉴权，再加功能。
- 中文文档和注释为主，技术术语可混合英文。

## 技术与架构偏好

- 传统主力为 Python、Flask、SQLite，偏轻量方案。
- 浏览器离线应用可接受单文件交付，但单文件是明确需求时必须真正保持单文件。
- 本地优先数据要有版本、迁移、owner 隔离、恢复和并发策略。
- Mock/Real 认证差异封装在 Provider，不在页面散落测试条件。
- API Key、OAuth token、登录态、cookie 和其他凭据默认脱敏，不进仓库和报告。

## 测试偏好

- 核心逻辑应测试，但不机械追求全面 TDD。
- 测试报告必须写类型和范围：smoke、单元、行为、构建、压力、CI、浏览器或用户验收。
- 交互系统重点测试重复点击、旧标签页、刷新、迁移、完成态和长程重复。
- 视觉/浏览器任务要真实打开并检查，不能只用字符串断言代替用户路径。

## 知识管理

- 用户高度重视经验积累，项目结束后期待项目总结、成功/失败经验、模式、决策和下一步。
- 知识要可移植、自包含、有交叉引用和生命周期。
- 公开文档可查的基础事实不大量复制；变化快的 API、平台和限额使用前重验。
- 未完成项目和失败案例也要记录，但状态必须真实。

## 工作原则速记

1. 空值优于假数据。
2. 实用优先，但不能用原型边界冒充正式产品。
3. 第二个实现时抽象。
4. v1 后先硬化。
5. 用户路径验证高于代码推断。
6. 配置变更先审计、备份、再修改。
7. 敏感信息默认脱敏。
8. 排他需求不做善意扩展。
9. 结论强度不超过证据强度。
10. 未验证就明确写未验证。
