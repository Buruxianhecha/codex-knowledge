## 核心偏好

### 软件安装
- **必须询问**再安装软件，不擅自操作
- **避免 C 盘**，除非别无选择
- **模仿已有风格**: 观察已有软件的安装位置和命名方式，保持一致
- 安装完成后**告知实际路径**
- **快捷方式必须有对应品牌图标**（不要让用户手动改图标）
- 安装后检查桌面快捷方式是否可见、是否可正常启动
- 用户指出安装问题后，必须重新验证最终用户体验，不只是"修代码"

### 品牌一致性
- 快捷方式名称和图标**必须匹配实际品牌**
- 不要用依赖工具（如 Ollama）的图标代替目标产品（如 DeepSeek）的图标
- 用户曾反馈"cloud code"打错→实际要"Claude Code"→错误命名的快捷方式要删干净

### 编码风格
- **实用主义**: 短变量名可接受（`THIN`, `P2C`, `MCW`, `MRH`）
- 模块级常量用短名，不追求"自文档化"的长名
- 但核心函数/类应有清晰命名

### 代码组织
- **快速原型风格**: 可以容忍 `sys.path.insert`、内联导入
- 先跑通再优化，不追求完美初始架构
- v1 完成后做一轮"硬化"（清理死代码、关 debug、统一配置）

### 时间/地区
- 时区硬编码为 UTC+8（中国用户）
- 中文注释和文档，技术术语可混合英文
- Codex/OpenClaw 默认用简体中文回复；除非用户明确要求英文，不要主动切换语言

### 测试
- 有测试基础设施（unittest 导入），但覆盖不追求全面
- 核心逻辑可加测试，但不过度推销 TDD

### 技术栈偏好
- Python 为主力语言
- Flask 用于 Web 应用
- SQLite 用于本地存储
- 优先轻量方案而非重量级框架

## 工作原则

1. **空值优于假数据**: 不可读区域留空，不做猜测填充
2. **实用优先**: 方案能跑通比架构优雅更重要（v1 阶段）
3. **第二个实现时抽象**: 同一接口出现两次 → 抽公共层
4. **v1 完成后加固**: 不立刻加功能，先清理债务
5. **对最终用户体验负责**: 不只是代码正确，要用户实际能用
6. **配置变更先审计再动手**: Provider/API/模型映射变更前先备份、列出现状、确认删除范围
7. **敏感信息默认脱敏**: API Key、bot token、GitHub token、gateway token 不进知识库和最终报告
