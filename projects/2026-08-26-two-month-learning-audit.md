# 2026-06-26 至 2026-08-26 两个月学习总审计

## 审计目标

本文件不是会话流水账，而是对最近两个月项目、写作、失败、决策和验证证据的总账。它回答四个问题：

1. 实际做过什么，哪些只是提出或计划过。
2. 哪些结果已经被远端仓库、CI、成品文档或真实交互验证。
3. 哪些结论可跨项目复用，值得进入长期知识层。
4. 哪些任务仍未闭环，未来不得误报为“已完成”。

审计范围固定为 `2026-06-26 00:00` 至 `2026-08-26 23:59`。更早内容只作为前因，不算本期新增。

## 证据等级

| 等级 | 定义 | 可以声称什么 |
|------|------|--------------|
| A | 远端仓库、提交 SHA、当前 HEAD 的 CI、回读 Blob 等可复核证据 | 已上传、当前版本测试通过、远端内容一致 |
| B | 成品文档、截图、工作簿、验收报告或可读取构建产物 | 成品存在；只能声称文档或截图实际展示的内容 |
| C | 用户明确确认或完整会话记录 | 需求、接受、纠正和当时执行结果成立 |
| D | 计划、说明书、待部署包、单方面完成声明 | 仅能写“已计划/已准备/待验证”，不能写“已上线成功” |

证据等级不等于作品价值。它只限制措辞强度：没有 A/B 级证据时，不能把“准备好”升级成“已运行成功”。

## 一、运行时与交付闭环

过去两个月最稳定的结论不是某个命令，而是“完成”有多层：

```text
代码/脚本退出 0
  -> 构建或测试通过
  -> 宿主应用接受结果
  -> 用户路径实际可用
  -> 重启、刷新、换标签页后仍成立
```

豆包案例只到第二层：修复编码后安装脚本成功，但客户端没有稳定接纳。拾光相册曾出现“最终上线”的强声明，随后深度验收却给出“暂不建议上线”。电视时钟的网页和仓库都能打开，但内容偏离排他需求，仍然不算完成。

因此，未来报告必须写清“验证到了哪一层”，而不是统一使用“完成”。

## 二、写作与研究方法

本期写作不是附属工作，而是形成了一套可复用的证据工程：

1. **来源分层**：本人/官方原始材料优先，其次机构记录、新闻和二次讨论。
2. **材料账本**：记录文件编号、时长、日期、链接和 SHA-256，保证分析对象可追溯。
3. **事实与解释分栏**：平台公告、法规、公开事件属于事实材料；动机、治理含义和传播机制属于分析。
4. **冲突裁决**：不以“出现次数最多”判真，比较来源距离、时间、原文和角色权限。
5. **强度匹配**：证据只支持“参与”时不能写“领导”；自述不能写成法律认定；单一案例不能推导总体因果。
6. **负面证据保留**：查不到、口径冲突、样本不足和资料截止日必须进入正文或局限。
7. **身份与元数据检查**：正文署名、文件名、作者属性和导出 PDF 元数据都不能泄露不应出现的真实姓名。
8. **多智能体收口**：角色可并行查证，但最终必须由统一的事实表和引用审计合并，不能直接拼接多份答案。

## 三、浏览器本地应用的状态工程

卡塞尔、剑来和拾光相册共同验证了：浏览器存储不是“随手塞 JSON”，而是一个需要版本、事务和隔离的数据库。

关键约束包括：

- 每条业务数据必须绑定稳定的 `userId` / `runId`。
- 版本迁移应先验证新版本；新版本损坏时仍要尝试有效旧版本，不能直接清空。
- 同一档案比较进度时使用单调字段，如 `storyCursor`、`actionSeq`、`turn`。
- 动作提交先读取可能更晚的持久化快照，再执行纯状态转换，同步写盘后才更新 UI。
- 新建或显式载入另一档案时，用 `activatedAt` 等激活序解决跨标签页竞争。
- 随机序章等随机结果只在创建时抽样，并随档案保存；读取时不得重新随机。
- 删除、回收站、完成态和死亡态也属于持久状态，刷新后不能“复活”。

## 四、交互规则与内容真实性

两个游戏项目暴露了两种“表面变化、实际重复”：

- 选项文案不同，但按第一/第二/第三位置套固定加减公式。
- 自由世界只替换回合编号，标题、正文和选项组合实质重复。

对应修复是把不变量写成可执行测试：

- 行动结果由动作文本、当前场景、风险和角色状态共同决定。
- 多个语义规则可以同时命中，例如“找宁姚学剑”同时改变人物关系和修行积累。
- 未识别意图可以推进并留下上下文，但不能凭空奖励固定属性。
- 内容去重前先去掉编号等装饰差异，再对标题、正文和选项做规范化指纹。
- 长程生成器必须跑压力测试；卡塞尔按五卷各 180 轮检查实质重复。

## 五、GitHub 发布与验证

本期形成的发布证据阶梯：

1. 本地测试通过。
2. 工作区形成完整、可运行快照。
3. 推送后读取远端默认分支和 HEAD。
4. 核对本地/远端提交或 Blob。
5. 只读取与 HEAD 对应的 CI 结论。
6. 最后检查 README、授权边界、敏感信息和实际入口。

凡人项目的第一条红 CI 很有价值：工作流在 `index.html` 推送前已经被触发，因此测试正确地报 `ENOENT`。后续 HEAD 已绿，说明“仓库最终成功”和“中间提交曾失败”可以同时为真。报告必须绑定 SHA，不能只说“CI 通过/失败”。

截至 2026-08-26，GitHub 官方规则仍包括：

- 浏览器上传单文件上限 25 MiB。
- 普通 Git 单对象强制上限 100 MiB，官方推荐单对象尽量不超过 1 MiB。
- 单次 push 强制上限 2 GiB。
- 仓库建议尽量低于 1 GB，低于 5 GB 属强烈建议。
- GitHub Pages 发布站点不超过 1 GB；软带宽限制 100 GB/月；默认构建软限制 10 次/小时。

这些属于时效知识，使用前要重新检查官方文档：

- [Repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)
- [Adding a file to a repository](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository)
- [About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
- [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

## 六、安全与隐私边界

- API Key、GitHub token、微信 `AppSecret`、OAuth `access_token`、抖音 `state.json` 和网页访问 token 都不得进入仓库。
- 测试站的“账户隔离”如果只依赖本地 `ownerId`，不能宣传为服务器端访问控制。
- 模拟手机号/微信登录必须明确标注模拟；切到真实认证需要服务端 callback 和凭据交换。
- 浏览器自动化不是官方 API；只操作本人账号、缩小对象范围、低频运行，出现安全验证或“操作频繁”立即停止。
- 对外文档不写真实姓名；署名和文档属性按用户当次要求设置。

## 八、知识准入结果

本期没有把所有记录都拆成核心条目。Android 贪吃蛇、Git 词表、单点占比图和 HVAC 工作簿等因缺少完成证据或复用价值，仅在本审计留痕。进入长期层的是：

- 应用侧验收高于命令成功。
- 证据强度决定结论强度。
- 浏览器状态是需要版本、事务和隔离的数据库。
- 交互系统需要单调进度、语义结算和规范化内容指纹。
- 测试结论必须与测试深度和具体 SHA 对齐。
- 排他性最小需求是合同，不能主动扩展。
- 认证模式应封装在 provider 边界。
- 发布前使用远端回读、HEAD CI 与敏感信息扫描。
