# 豆包本地电脑工作环境故障处理

> 详细恢复版。保留当时可复用的故障分层，但不公开具体 Windows 用户名，也不把一次实例修补写成客户端根因已经确定。

## 基本信息

- **日期**：2026-06-30
- **目标**：处理豆包桌面端“初始化本地电脑工作环境失败”。
- **最终状态**：某个 sandbox 实例的脚本层修复成功；客户端层未稳定闭环，项目按未完成/失败经验记录。
- **主要环境特征**：Windows、非 ASCII 用户目录、客户端动态生成 sandbox 环境。

## 已确认事实

1. 找到了当时客户端实际使用的一个 sandbox 实例。
2. 该实例的 `postinstall.py` 在文件读取/路径处理链中出现与非 ASCII 环境相关的问题信号。
3. 对该实例的相关读取显式处理 UTF-8 后，手动执行 `prepare.ps1` 能走到成功结束。
4. 当次环境目录和部分产物可见。
5. 豆包 UI 没有稳定完成“本地电脑工作环境初始化”的最终接纳。
6. 历史实例曾被客户端清理或替换，说明“修改一个生成后的目录”不是稳定修复入口。

## 证据没有证明什么

- 没有证明“中文用户名”是唯一根因。
- 没有证明 `postinstall.py` 是客户端初始化流程的唯一失败点。
- 没有证明一次 `prepare.ps1` 成功会让客户端登记该环境为可用。
- 没有证明补丁会自动作用于后续新生成实例。

因此更准确的说法是：**在一个具体动态实例里发现并绕过了编码/路径相关故障，但宿主客户端的选择、校验和接纳机制仍未查清。**

## 故障分层

| 层级 | 检查对象 | 本次结果 |
|------|----------|----------|
| L1 文件读取 | 脚本能否正确读取目标文件/路径 | 实例修补后通过 |
| L2 安装命令链 | `prepare.ps1` 是否完成 | 当次通过 |
| L3 环境产物 | 目录和依赖是否生成 | 当次可见 |
| L4 客户端接纳 | 客户端是否登记/选择该环境 | 未稳定通过 |
| L5 功能调用 | 用户实际功能是否使用该环境 | 未充分验证 |
| L6 重启保持 | 重启/重建后是否仍成立 | 未通过或未确认 |

本次最重要的错误，是把 L2 的成功过早解释成 L4-L6 的成功。

## 为什么修单个实例不够

动态环境可能按版本、会话、哈希或健康检查重新生成。直接修改生成物会遇到：

- 下一次启动改用另一个实例。
- 更新/清理流程覆盖补丁。
- 客户端检查 manifest、版本、完成标记或完整性。
- 生成器再次输出同样有问题的脚本。
- 子脚本成功退出，但宿主没有接收到它期望的状态。

稳定修复更可能需要找到：生成模板、环境创建器、客户端登记流程、健康检查或接纳条件。

## 下次排障路径

1. 启动前记录候选环境目录、mtime、大小和关键文件哈希。
2. 启动客户端并记录新建/删除/改写的目录。
3. 记录进程命令行、父子进程和实际被调用脚本。
4. 对比成功/失败实例的 manifest、完成标记、日志与配置引用。
5. 搜索生成 `postinstall.py` 的上游模板/资源，而不是继续手改副本。
6. 追踪客户端何时删除旧环境，以及删除前最后一个健康检查/日志事件。
7. 修复后验证 UI、实际功能调用、重启和下一次环境重建。

## 编码与路径检查

对 Windows 非 ASCII 环境，分别检查：

- 源脚本自身编码。
- `open(..., encoding=...)` / PowerShell 读写编码。
- console/log encoding。
- subprocess 参数传递与 quoting。
- 路径规范化、空格和非 ASCII 字符。
- Windows PowerShell 与 PowerShell 7 的差异。

不要写死任何具体用户主目录。公开文档统一用 `%USERPROFILE%`；需要覆盖非 ASCII 场景时，把它作为测试维度描述为 `<NON_ASCII_HOME_TEST_CASE>`，而不是写出 `C:\Users\...` 形式的用户名示例。

## 可复用结论

- 命令退出码只能证明该命令，不证明宿主应用接受结果。
- 自动再生目录中的手工补丁默认视为临时补丁。
- 修生成物之前先找生成源。
- 非 ASCII 路径问题要把文件编码、路径、日志、子进程和宿主接纳分开验证。
- 没有 UI/功能/重启层证据时，必须明确写“脚本层通过，应用层未完成”。
